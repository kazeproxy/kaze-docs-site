    性能调优¶

    默认设置已经适合大多数节点：内存上限、多用户认证的优化都是自动开启的，不用配置。这页是人多、带宽大、机器小的时候值得检查的几项。改了 kaze.conf 后执行 kaze restart 生效。

    内核参数¶

    Linux 默认的网络参数偏保守，跑代理节点时最影响速度的是拥塞控制和缓冲区。把下面的内容写进 /etc/sysctl.d/99-kaze.conf，然后执行 sysctl --system：

    # 拥塞控制用 BBR（内核 4.9 以上）。对 TCP 节点的速度影响最大
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr

# 连接队列：人多时新连接不被丢弃
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096

# 节点要向外发起大量连接，放宽本机可用的端口范围
net.ipv4.ip_local_port_range = 1024 65535

# 连接空闲一会儿后不重新慢启动，线路稳定时吞吐更好
net.ipv4.tcp_slow_start_after_idle = 0

# 系统可同时打开的文件（连接）总数
fs.file-max = 1048576

# UDP 缓冲区：Hysteria2 / TUIC / Mieru UDP 走 UDP，默认值大带宽时会丢包
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216

    应用后检查 BBR 是否生效：

    sysctl net.ipv4.tcp_congestion_control   # 应输出 bbr

    不要照搬 TCP 缓冲区

    网上常见的 net.ipv4.tcp_mem、tcp_rmem、tcp_wmem 三项和机器内存直接相关：设得太大，人多时会把内存吃满；太小又跑不满带宽。上面的配置没有改它们，Linux 会按内存自动调整。确实要调时，一次只改一项，观察几天再决定：内存还剩很多但速度上不去，适当加大；内存经常吃满，就调小。

    开了 TCP Brutal 的多路复用会话，按 Brutal 的速率发送；其余连接都用上面设置的 BBR。

    文件描述符¶

    每条连接占一个文件描述符。一键安装的服务单元里已经写了 LimitNOFILE=1048576，Docker 示例里对应 ulimits: nofile: 1048576；手动安装请照手动安装的单元写上。没有这一项时，几千个连接后会出现 too many open files。

    内存与垃圾回收¶

    kaze 默认把内存软上限设为机器内存（或容器的内存限制）的 70%：快到上限时垃圾回收会更勤快，而不是等进程被系统杀掉。和别的服务共用一台机器时，按能分给 kaze 的量填一个数：

    memory_limit=0        # MB。0 = 自动（70%）；off = 不限制；例：memory_limit=400

    还可以用 Go 运行时的两个环境变量进一步调：

    环境变量 作用 什么时候用
    GOGC 垃圾回收的频率，默认 100。调小（如 50）内存更省、CPU 略高；调大（如 200）CPU 更省、内存更高 内存小的机器设 50；内存充裕、CPU 吃紧时设 200
    GOMEMLIMIT 内存软上限，如 400MiB。设了它就以它为准，memory_limit 不再生效 一般不用，memory_limit 已经够了

    参考搭配：

    机器内存 建议
    512 MB memory_limit=350，加环境变量 GOGC=50
    1 GB 默认即可
    2 GB 以上、人多 默认即可；CPU 吃紧时加 GOGC=200

    环境变量的设置方法：

    systemctl edit kaze        # 多实例时是 kaze-NAME

    在打开的编辑器里写：

    [Service]
Environment="GOGC=50"

    保存后执行 systemctl restart kaze。

    在 environment: 下加一行：

    GOGC: "50"

    然后 docker compose up -d。

    多用户认证的开销¶

    一个端口上有很多用户时，节点要先认出每个新连接是谁。不同协议的代价差别很大：

    协议 怎么认出用户 实测（1 万个用户）
    Shadowsocks 2022（多用户） 客户端带了身份标识，直接查到 每个连接约 8 微秒，和用户数无关
    VMess 每个用户只需解一个 16 字节的块 全部用户试一遍约 0.1 毫秒
    VLESS、Trojan、Hysteria2、TUIC、AnyTLS 等 按 UUID / 密码直接查 和用户数无关
    Shadowsocks 经典加密（aes-gcm、chacha20 等） 没有身份标识，只能拿每个用户的密码逐个试 每个用户约 0.7 微秒；1000 个用户全试一遍约 0.7 毫秒，1 万个约 7 毫秒

    （单核实测，Apple M4。）

    所以只有 Shadowsocks 经典加密会随用户数变慢，大量新连接同时到来时 CPU 会明显升高。kaze 对它内置了三层处理，默认全部开启，不用配置：

    1. 最近登录过的用户先试：活跃用户换了 IP 重新连，通常第一个就试中。
    2. 限制同时进行的全量查找：用户列表刚更新、大量连接同时进来时，CPU 不会被一下占满。
    3. 一直认不出的地址暂停全量查找：扫描器、密码已经失效的客户端反复来连时，不会每次都把所有用户试一遍。

    用户在一千以上、又要用 Shadowsocks 时，建议改用 2022-blake3-aes-128-gcm，认证开销和用户数无关，见 Shadowsocks。

    对付故意用错误密码反复连接的攻击，TCP 上的协议还有一套通用的防爆破设置（invalid_access_*，Hysteria2 / TUIC 不在其中）：同一个 IP 短时间内失败太多次就暂时封禁，见配置项速查表。开启前要确认节点能拿到用户的真实 IP（经过中转时见真实 IP），否则会把中转机整体封掉。

    空闲超时¶

    tcp_timeout=5         # 分钟，TCP 连接空闲多久断开
udp_timeout=2         # 分钟，UDP 会话空闲多久结束

    连接数很高的节点可以调小，让空闲连接早点释放；跑长连接应用（SSH、IM 推送）的节点调大一点，避免被断。

    节点总带宽¶

    node_speed_limit=0    # Mbps，整个节点的上限。0 = 不限

    机器带宽有上限、又不想被少数人打满时设置；配合动态限速用效果更好。

    日志量¶

    人多时 info 级别的日志（每次同步用户、每条被屏蔽的连接）会写很多。稳定后改成：

    log_level=warn

    排错时再临时改回 info 或 debug。

    端口跳跃什么时候用¶

    Hysteria2 / TUIC 的单个 UDP 端口被运营商限速或封锁时，开端口跳跃让客户端在一段端口里换着连。转发在内核里完成，对 kaze 没有额外开销；端口没被针对时不需要开。
