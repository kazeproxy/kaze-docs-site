    Shadowsocks¶

    Shadowsocks 是最普及的加密代理协议，几乎所有客户端都支持，不需要域名和证书，TCP 和 UDP 走同一个端口。它本身不伪装成任何东西，需要外观时可以叠加 kaze 内置的 simple-obfs 或 Shadow TLS v3。想要更强的抗探测，看 VLESS + REALITY；想要最广的兼容、最少的配置，Shadowsocks 合适。

    推荐组合¶

    • 首选：2022-blake3-aes-128-gcm。主流客户端都支持，用户多时认人快，带时间戳防重放。要求客户端时间准确，和节点相差 30 秒以上会被拒绝。
    • 备选：aes-128-gcm。兼容最好，密码就是用户 UUID，不看时间。用户多时新 IP 的第一个连接要逐个试用户密钥（kaze 会记住每个 IP 上次的用户来缓解，见加密方式怎么选）。
    • 需要 TLS 外观时：上面任一加密 + 插件 Shadow TLS（version=3），不需要域名和证书，也不用另跑 shadow-tls 程序。

    面板里怎么填¶

    节点管理 → 添加节点 → 选 Shadowsocks。节点名称、节点地址、连接端口 / 服务端口、权限组、倍率和其它协议一样填。协议相关的字段：

    面板字段 填什么
    加密算法 推荐 2022-blake3-aes-128-gcm。这是可搜索的选择框，预设只有 7 种；要用 xchacha20-ietf-poly1305、aegis-128l 等扩展算法，在搜索框里输入名字，再点「使用 "xxx"（自定义）」，面板会原样下发给节点。不要选 2022-blake3-chacha20-poly1305，见加密方式怎么选
    插件 不用插件选 None；混淆选 Simple Obfs；TLS 外观选 Shadow TLS。V2Ray Plugin、Gost Plugin、ResTLS、KCPTun 节点不内置，见插件
    插件选项 选了插件就必须填（留空时订阅里不会带插件）。Simple Obfs：obfs=http;obfs-host=www.bing.com（或 obfs=tls）；Shadow TLS：host=伪装域名;password=密码;version=3
    客户端指纹 只在 Shadow TLS / ResTLS 时出现，给客户端用，节点不看

    2022 加密的服务端密钥由面板自动生成并下发，节点上不用填。用 Shadow TLS 时连接端口和服务端口填同一个。

    节点管理 → 添加节点 → Shadowsocks。协议相关的字段：

    面板字段 填什么
    加密算法 下拉框里 6 种：aes-128-gcm、aes-192-gcm、aes-256-gcm、chacha20-ietf-poly1305、2022-blake3-aes-128-gcm、2022-blake3-aes-256-gcm。推荐 2022-blake3-aes-128-gcm
    混淆 无，或 HTTP（simple-obfs 的 http 模式），选 HTTP 后可填路径和 Host

    V2board 的 Shadowsocks 节点没有插件字段，不能用 Shadow TLS，也没有 simple-obfs 的 tls 模式。2022 的服务端密钥由面板下发。节点配置里 server_type=ss。

    在服务器里启用 Shadowsocks 协议，设端口和加密方式。

    • 2022 加密要填服务端密钥。kaze 按原文使用这串密钥，长度要正好是 16 个字符（2022-blake3-aes-128-gcm）或 32 个字符（2022-blake3-aes-256-gcm），否则节点起不来。
    • 混淆字段只支持 http；插件支持 simple-obfs（http / tls）和 Shadow TLS（版本要选 3）。v2ray-plugin、gost-plugin、restls、kcptun 不支持，启动日志会写明。
    • 节点配置里 server_type=ss（或 shadowsocks），见对接 PPanel。

    经典加密：

    type=local
server_type=ss
port=8388
cipher=aes-128-gcm
users=alice:密码1,bob:密码2

    2022 加密：

    type=local
server_type=ss
port=8388
cipher=2022-blake3-aes-128-gcm
server_key=MDEyMzQ1Njc4OWFiY2RlZg==
users=alice:4f8a1c2e-0000-4000-8000-000000000001
    键 说明
    server_type ss 或 shadowsocks
    port 监听端口，TCP 和 UDP 同一个
    cipher 加密方式，可选值见加密方式怎么选
    server_key 只有 2022 加密要填，必填。用 openssl rand -base64 16 生成（2022-blake3-aes-256-gcm 用 32）
    users 名字:密钥，逗号隔开，名字和密钥都不能重复
    plugin / plugin_opts 可选。混淆：plugin=obfs + plugin_opts=obfs=http;obfs-host=www.bing.com（或 obfs=tls）；Shadow TLS：plugin=shadow-tls + plugin_opts=host=伪装域名;password=密码;version=3

    users 里的密钥：经典加密就是客户端填的密码；2022 加密要写 UUID，不要写 base64 密钥（kaze 会把它当 UUID 截取，算出的用户密钥就对不上了），客户端的密码也不是这个 UUID，而是 服务端密钥:用户密钥 一整串。运行 kaze check 会打印每个用户的客户端密码（alice: client password ...），照抄给客户端。更多见不接面板，直接搭节点。

    节点配置¶

    接面板时节点这边只要写面板信息，加密、端口、插件、2022 服务端密钥都由面板下发。Shadowsocks 不需要 TLS 证书（Shadow TLS 借用伪装站的握手，也不需要）。

    type=xboard
node_id=1
panel_url=https://panel.example.com
panel_key=通讯密钥

    V2board 和 PPanel 要加 server_type=ss（PPanel 的 node_id 是服务器 ID）。防火墙要同时放行这个端口的 TCP 和 UDP。

    启动后看日志里的 listening 一行，transport 字段会写出实际提供的组合，例如 tcp+shadow-tls+2022-blake3-aes-128-gcm、tcp+obfs-http+aes-128-gcm，可以用来确认面板设置是否生效。

    加密方式怎么选¶

    加密方式 客户端 说明
    2022-blake3-aes-128-gcm 主流客户端 首选。用户多也能直接认出是谁；带时间戳，防重放；客户端时间要准（±30 秒）
    2022-blake3-aes-256-gcm 主流客户端 同上，密钥更长
    aes-128-gcm 几乎所有 兼容首选。密码就是 UUID，不看时间
    aes-192-gcm、aes-256-gcm 几乎所有 同上
    chacha20-ietf-poly1305 几乎所有 兼容好，但在节点上明显慢于 AES-GCM（见下方实测）
    xchacha20-ietf-poly1305 部分 只为兼容
    aegis-128l、aegis-256 仅 mihomo / Clash.Meta 类 最快，但客户端少
    aez-384、deoxys-ii-256-128、ascon128、ascon128a、lea-128-gcm、lea-192-gcm、lea-256-gcm、rabbit128-poly1305 仅 mihomo / Clash.Meta 类 比 AES-GCM 慢、客户端少，只为兼容已有配置，不推荐专门选

    单核速度参考（Apple M4）：aegis-128l 约 20 GB/s，aes-128-gcm 约 9 GB/s，chacha20-ietf-poly1305 约 1.4 GB/s。大多数节点的瓶颈在带宽而不在加密，所以不必为了速度换成只有少数客户端能用的算法。

    经典加密（aes-gcm、chacha20 等）用户多时：协议里没有用户标识，节点要拿每个用户的密钥试解。kaze 先试这个 IP 上次认出的用户，再试 15 分钟内活跃过的用户，最后才全表查找，所以老用户通常一次就中，只有新 IP 的第一个连接要多花些 CPU。一个 IP 一分钟内 10 次全表查找都没找到人（扫描器、用着旧密码的客户端），之后 10 分钟这个 IP 每秒只给查一次。用户几千人的节点建议用 2022。

    不支持 2022-blake3-chacha20-poly1305

    SS2022 的多用户身份头只定义在 AES 上。Xboard 给这种加密生成的是「服务端密钥:用户密钥」两段密码，但不给节点下发服务端密钥；mihomo 和 sing-box 拿到这种组合也会直接拒绝加载（Shadowsocks 2022 EIH support only available in AES ciphers）。请改用 2022-blake3-aes-128-gcm 或 2022-blake3-aes-256-gcm。

    2022 的密码：客户端密码是 服务端密钥:用户密钥，用户密钥由用户 UUID 转成 base64（Xboard 和 kaze 算法一致）。接面板时这串由面板写进订阅；本地模式用 kaze check 打印。

    插件：simple-obfs 与 Shadow TLS¶

    插件 节点 用途
    simple-obfs（http / tls） 内置，不需要另装 obfs-server 伪装成 HTTP 请求或 TLS 握手：免流的 Host 混淆、只放行 HTTP / HTTPS 的网络。对所有加密方式都可用
    Shadow TLS v3 内置，不需要另跑 shadow-tls，也不多占端口 和真实网站完成真正的 TLS 握手，外观就是访问那个网站
    v2ray-plugin、gost-plugin、kcptun、restls 不内置 节点只提供不带插件的 Shadowsocks，并在日志里提示；要用得自己在前面跑插件的服务端

    simple-obfs

    • Xboard：插件选 Simple Obfs，插件选项 obfs=http;obfs-host=www.bing.com 或 obfs=tls;obfs-host=www.bing.com。插件名写 obfs、obfs-local、simple-obfs、obfs-http、obfs-tls 节点都认。
    • 用 obfs= 而不是 mode= 写模式：节点两种都认，但 Xboard 给 Surge、Stash、Loon、Quantumult X 等生成订阅时只读 obfs= 和 obfs-host=。
    • 本地模式：plugin=obfs + plugin_opts=obfs=http;obfs-host=www.bing.com。
    • obfs-host 是给客户端用的伪装域名，节点不校验。
    • simple-obfs 的 tls 模式只是模仿 TLS 的样子，不是真的 TLS 握手。想要真实的 TLS 外观用 Shadow TLS。

    Shadow TLS v3

    • 插件选 Shadow TLS，插件选项 host=伪装域名;password=密码;version=3。伪装站选一个支持 TLS 1.3、节点能正常访问 443 的大站，password 自己随便定一串。
    • 必须写 version=3。不写时面板给客户端的订阅是 v2，节点只提供 v3，会直接报错不启动。
    • 面板的连接端口和服务端口填同一个。
    • 和 simple-obfs 二选一，不能叠加。

    订阅排障¶

    以下是 Xboard 生成订阅时的行为，客户端连不上或看不到节点时按顺序查：

    1. 客户端里根本没有这个节点：Xboard 按客户端格式过滤加密方式。老 Clash 格式和 SIP008 只放 aes-128-gcm、aes-192-gcm、aes-256-gcm、chacha20-ietf-poly1305 的节点；Surge 再多两种 2022 AES；Stash 要 3.0.0 以上才给 2022 节点。扩展算法（aegis-128l 等）只有 Clash Meta 格式的订阅能用，换用 mihomo / Clash.Meta 类客户端。
    2. 选了插件，订阅里却没有插件：Xboard 只在「插件」和「插件选项」都不为空时才把插件写进订阅。插件选项留空时，Simple Obfs 节点上仍按 http 混淆提供，客户端却不带混淆，必然连不上——把插件选项填完整。
    3. 混淆模式或 Host 对不上：Clash Meta 订阅里插件选项没写模式时按 http、没写 Host 时按 www.bing.com；Surge、Stash、Loon、Quantumult X 只读 obfs= 和 obfs-host=。统一写成 obfs=http;obfs-host=域名 最稳。
    4. Shadow TLS 连不上：插件选项里有没有 version=3（没有时订阅给的是 v2）；连接端口和服务端口是否相同。Shadowrocket 拿 ss:// 一行式订阅时解析不出 Shadow TLS 插件，处理办法见对接 Xboard。
    5. 2022 节点突然全部连不上：订阅里的服务端密钥由节点的创建时间算出。删掉重建节点、或把加密在 128 和 256 之间切换后，服务端密钥变了，节点会自动拿到新密钥，但用户手里的旧订阅还是旧密码——让用户更新订阅。
    6. 2022 节点个别用户连不上：多半是客户端设备时间不准（相差 30 秒以上）。把节点的 log_level 调成 debug，日志里该用户 IP 的 handshake failed 会写明原因。

    客户端怎么连¶

    订阅会自动带上加密方式、密码和插件。手动配置时要填：

    项 填什么
    服务器 / 端口 节点地址和连接端口
    加密方式 和节点一致
    密码 经典加密：用户 UUID（本地模式是 users 里的密钥）；2022：服务端密钥:用户密钥，从订阅里复制，本地模式用 kaze check 打印的那串
    插件 混淆：mihomo / Clash.Meta 写 plugin: obfs，plugin-opts 里 mode: http（或 tls）、host: 伪装域名；Shadowrocket 插件选 simple-obfs / obfs-local。Shadow TLS：mihomo 写 plugin: shadow-tls，plugin-opts 里 host、password、version: 3

    mihomo / Clash.Meta 示例：

    - name: 节点名
  type: ss
  server: 节点地址
  port: 8388
  cipher: 2022-blake3-aes-128-gcm
  password: "服务端密钥:用户密钥"
  udp: true

    常见问题¶

    日志里出现「shadowsocks: unsupported cipher」 → 面板下发的加密方式节点不认识：多半是选了 2022-blake3-chacha20-poly1305，或自定义算法名打错了 → 改成加密方式怎么选表里的名字。

    日志里出现「shadow-tls version 2 is not supported; kaze serves version 3」 → Shadow TLS 插件选项没写 version=3（或写了别的版本），面板默认给客户端 v2 → 插件选项加上 version=3，让用户更新订阅。

    日志里出现「shadow-tls needs host= and password= in the plugin options」 → Shadow TLS 插件选项不完整 → 写成 host=伪装域名;password=密码;version=3。

    日志里出现「this Shadowsocks plugin is not built in; the node serves plain Shadowsocks」 → 选了 v2ray-plugin、gost-plugin、restls、kcptun 等不内置的插件，节点只提供不带插件的 Shadowsocks，订阅里的客户端仍带插件，连不上 → 换成 Simple Obfs 或 Shadow TLS，或自己在前面跑插件的服务端。

    日志里出现「shadowsocks: server key must be 16 bytes in base64」（或 32 bytes） → 2022 服务端密钥长度不对。本地模式：server_key 用 openssl rand -base64 16（256 位算法用 32）重新生成；PPanel：服务端密钥按原文使用，要正好 16 / 32 个字符。

    日志里出现「Shadowsocks over ws is not supported」 → 节点设了 WebSocket 等传输，Shadowsocks 只跑在 TCP 上 → 传输改为 TCP；要外观用插件。
